## Что сейчас мешает (проверено по коду)
1. **Имена файлов с дефисом.** В имени web resource разрешены только буквы, цифры, точки и `/`. Сейчас дефис есть в `ui/appeal-modal.ts`, `ui/criteria-table.ts`, `views/checklist-editor.ts`.
2. **Автомонтирование.** `web/src/main.ts:128-129` монтирует приложение в любой `#app` с `apiBase: '/api'`. Загрузчику D365 нужно своё монтирование.
3. **Нет CORS.** В `server/app.py` нет `CORSConfig`, а из D365 запросы идут с origin организации. `api.ts:56-58` шлёт `Content-Type: application/json`, поэтому браузер делает preflight.
4. **Нет способа передать настройки.** D365 пропускает только свои query-параметры (`data`, `id`, `typename`, `orglcid`, …). `apiBase` и стартовый маршрут должны приходить в `data`.
5. **Ресурсы редизайна.** Логотипы в `web/assets/*.svg` и шрифт в CSS: SVG и CSS разрешены, `.woff2/.ttf` нет. Пути только относительные, `/WebResources/...` нельзя.

## Что сделать
1. **Переименуй модули без дефиса:** `appealModal`, `criteriaTable`, `checklistEditor`. Обнови импорты, проверь `tsc`. Бандлер не добавляй: это ограничение редизайна, и переименование снимает риск с именами дешевле.
2. **Убери автомонтирование из `main.ts`.** `main.ts` только экспортирует `mountCqa`. Монтирование переезжает в `web/index.html` (модульный скрипт для локальной страницы, как сейчас, `apiBase: '/api'`).
3. **Загрузчик `web/d365/index.htm`.** Читает `data` из `location.search` как JSON: `{ "apiBase": "https://…/api", "route": "#/dialogs/DEV" }`. При битом JSON показывает понятный баннер, а не пустой экран. Монтирует в свой корень (не `#app`). Если пришли `id`/`typename`, передаёт их в опции для будущей привязки к записи и ничего не ломает. Повторная загрузка iframe (форма D365 пересоздаёт его при смене вкладки) не плодит таймеры и слушатели: используй функцию размонтирования, которую возвращает `mountCqa`.
4. **Пути.** Все URL внутри UI (логотип, шрифт, скрипты) считай относительно модуля (`new URL('../assets/logo-cqa-light.svg', import.meta.url)`) или CSS-файла. Нигде нет `/static/...`, `/assets/...` от корня. Проверь `grep` по `web/src`, `web/cqa.css` и `index.html`.
5. **CORS на сервере.** `Litestar(cors_config=CORSConfig(allow_origins=…))` (Litestar 2.25). Список origin берётся из env `CQA_ALLOWED_ORIGINS` через запятую. Если env пуст, CORS выключен и поведение как сейчас. Добавь переменную в `.env.example` с комментарием. Тест в `tests/` проверяет, что preflight с разрешённого origin проходит, а с чужого нет.
6. **Аудио звонков.** `audio_url` указывает на подписанную ссылку Dynamics, а в строгом CSP нужен один origin. Если успеваешь, сделай прокси `GET /api/conversations/{cid}/audio` (рекомендация 4 из R4). Если нет, оставь как есть и запиши ограничение в документацию. Ссылки на доказательства и перемотку не ломай.
7. **Пакет web resources.** Скрипт `scripts/package_d365.py` собирает `out/d365/`: `cqa_/index.htm`, `cqa_/cqa.css`, `cqa_/dist/**/*.js`, `cqa_/assets/*.svg`. Каждое имя проверяется регуляркой из ограничений (буквы, цифры, точки, одиночные `/`), размер каждого файла меньше 5 MB, типы файлов только разрешённые. При нарушении скрипт падает с понятной ошибкой. Без новых зависимостей.
8. **Стили.** Всё под `.cqa`, глобальные `html/body` только в `standalone.css`, который в пакет не попадает. Внутри iframe нет горизонтального скролла при ширине 390 и 1024 px.

## Как доказать (локальный стенд вместо D365)
Настоящего D365 trial нет. Если он понадобится, спроси меня, сам ничего не регистрируй. Собери стенд, который воспроизводит условия D365:
- Сервер CQA на одном порту, например `8791`, с `CQA_ALLOWED_ORIGINS=http://127.0.0.1:8792`.
- Отдельный статический сервер на `8792` раздаёт `out/d365/` и страницу-хост `host.html`. Хост открывает `cqa_/index.htm?data=<encodeURIComponent(JSON)>` в `<iframe>` без `sandbox`, как форма D365 с выключенным «Restrict cross-frame scripting». Стенд положи в `scripts/d365_harness/` или в `docs/internal/redesign/`, не в `web/`.
- **CSP ставится HTTP-заголовком `Content-Security-Policy` на ответ `cqa_/index.htm`** (и на остальные файлы `cqa_/`), не `<meta>` в `host.html`. Политика хоста не действует на документ iframe, загруженный по URL. Поэтому его `fetch`, шрифты и скрипты регулирует только CSP самого `index.htm`. `frame-ancestors` в `<meta>` браузер игнорирует, его можно задать только заголовком. Статический сервер стенда сам выбирает политику по ключу (env или query на сервере, не в `data`). Прогоны три:
  - **по умолчанию** из R4 (`script-src * 'unsafe-inline' 'unsafe-eval' blob:; style-src * 'unsafe-inline' blob:; … frame-ancestors 'self' http://127.0.0.1:8792`): всё работает;
  - **строгий без API** (`default-src 'self'; connect-src 'self'; font-src 'self'; frame-ancestors http://127.0.0.1:8792`): запросы к `8791` блокируются CSP, и в UI видна понятная ошибка, а не пустой экран;
  - **строгий с API** (то же плюс `connect-src 'self' http://127.0.0.1:8791`; `media-src` для аудио; `font-src data:`, если шрифт в base64): всё работает.
  В каждом прогоне проверь по событиям `securitypolicyviolation` и консоли фрейма, что нарушения ровно ожидаемые. Отдельно проверь `frame-ancestors`: хост с другого origin не может встроить `index.htm`. Без этих заголовков стенд проходит проверку CSP ложно.
- Playwright (пример в `docs/internal/redesign/capture.cjs`): в iframe открываются все 7 маршрутов; запросы идут кросс-доменно на `8791`; в консоли нет ошибок CORS и CSP; логотип и шрифт загрузились; пересоздание iframe 3 раза не дублирует запросы и слушатели; невалидный `data` даёт баннер. Сделай скриншоты стенда на 1440 и 390.
- Сценарии с POST (апелляция, решение, сохранение чек-листа) прогоняй на копии store.
