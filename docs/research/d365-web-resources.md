# Embedding the CQA UI in Dynamics 365 as an HTML web resource (R4, #33)

Question: can `web/` (plain ES modules, `mountCqa(root, {apiBase})`, styles under `.cqa`) run inside a Dynamics 365 / model-driven app as an HTML web resource, and what has to change? Sources are Microsoft Learn (checked 2026-11-07) and MDN. Claims marked **[INFERENCE]** are not stated by a source and need a check in a real environment.

## Constraints

| Topic | What the platform does | Effect on this repo |
|---|---|---|
| File types and size | Web resources are virtual files stored in Dataverse: `.htm/.html`, `.css`, `.js`, `.png/.jpg/.gif/.svg/.ico`, `.xml/.xsl`, `.resx`. The upload limit is `Organization.MaxUploadFileSize`, **5 MB by default** ([web resources](https://learn.microsoft.com/en-us/power-apps/developer/model-driven-apps/web-resources)). | `web/dist` is 88 KB and `cqa.css` 28 KB, so size is fine. Everything we ship is an allowed type. |
| Names | A name «can only include letters, numbers, periods, and nonconsecutive forward slash ("/") characters», and the publisher prefix is prepended ([create/edit web resources](https://learn.microsoft.com/en-us/power-apps/maker/model-driven-apps/create-edit-web-resources)). | **Blocker:** `ui/appeal-modal.js`, `ui/criteria-table.js` and `views/checklist-editor.js` contain `-`, so they can't be uploaded under these names. |
| Links between files | Use relative URLs between web resources, and simulate folders with `/` in names. Don't use `/WebResources/...` as a root path ([web resources](https://learn.microsoft.com/en-us/power-apps/developer/model-driven-apps/web-resources), [HTML web resources](https://learn.microsoft.com/en-us/power-apps/developer/model-driven-apps/webpage-html-web-resources)). | Our imports are already relative (`./views/…`, `../ui/…`). Upload them as `cqa_/dist/main.js` and so on. **[INFERENCE]** A `<script type="module">` resolves those relative imports the same way as a classic `<script src>`; MS docs don't mention ES modules, so check it once in a dev environment. |
| Hosting on a form | An HTML web resource on a form is an IFRAME. The form runtime **may destroy and re-create it**, for example on tab switches, so initialization must be idempotent ([HTML web resources](https://learn.microsoft.com/en-us/power-apps/developer/model-driven-apps/webpage-html-web-resources), [getContentWindow](https://learn.microsoft.com/en-us/power-apps/developer/model-driven-apps/clientapi/reference/controls/getcontentwindow)). It can also open as a full page or dialog with `Xrm.Navigation.navigateTo({pageType: "webresource", webresourceName, data})` ([navigateTo](https://learn.microsoft.com/en-us/power-apps/developer/model-driven-apps/clientapi/reference/xrm-navigation/navigateto)). | `mountCqa` replaces the root's children and returns an unmount function, so re-mounting is safe. Hash routing (`#/…`) lives inside the IFRAME. |
| Query parameters | Only `typename, type, id, orgname, userlcid, orglcid, data, formid` (plus internal ones) are accepted; «the web resource will not open if other parameters are used». Custom configuration goes into `data` ([HTML web resources](https://learn.microsoft.com/en-us/power-apps/developer/model-driven-apps/webpage-html-web-resources), [form properties](https://learn.microsoft.com/en-us/power-apps/maker/model-driven-apps/web-resource-properties-legacy)). | `apiBase` (and the group or conversation id) must arrive in `data`, not as our own query parameters. |
| Access to `Xrm` | A web resource on a form may use `parent.Xrm.Page` / `parent.Xrm.Utility`, but not globals defined by form scripts. It should load its own libraries ([HTML web resources](https://learn.microsoft.com/en-us/power-apps/developer/model-driven-apps/webpage-html-web-resources)). | We need no `Xrm` to work. The optional record context comes from the `id`/`typename` parameters. |
| Sandbox | «Restrict cross-frame scripting» sets `sandbox=""`, which applies all restrictions and can stop scripts from running ([IFRAME and web resource controls](https://learn.microsoft.com/en-us/power-apps/developer/model-driven-apps/use-iframe-and-web-resource-controls-on-a-form)). | The option must stay **off** for our control. |
| CSP | Default CSP when enforced: `script-src * 'unsafe-inline' 'unsafe-eval' blob:; style-src * 'unsafe-inline' blob:; …; frame-ancestors 'self' https://*.powerapps.com`. **Strict CSP** sets `default-src 'self'` and `connect-src 'self' blob: data: wss: <platform>`, with `connect-src` customizable per environment ([Power Platform CSP](https://learn.microsoft.com/en-us/power-platform/admin/content-security-policy)). | The default CSP is fine: no `eval`, `innerHTML` or inline script in `web/src`. Under Strict CSP an admin must add our API origin to `connect-src`. **[INFERENCE]** Call audio falls back to `default-src 'self'` because no `media-src` is listed ([MDN default-src](https://developer.mozilla.org/docs/Web/HTTP/Headers/Content-Security-Policy/default-src)), so it would be blocked unless served from an allowed origin. |
| Calling our API | The page origin is the Dynamics org, so calls to the CQA API are cross-origin. `fetch` with `Content-Type: application/json` triggers a CORS preflight ([MDN CORS](https://developer.mozilla.org/docs/Web/HTTP/Guides/CORS)). An HTTPS page can't fetch `http://` ([MDN mixed content](https://developer.mozilla.org/docs/Web/Security/Mixed_content)). Litestar enables CORS with `Litestar(cors_config=CORSConfig(allow_origins=[…]))` ([Litestar middleware](https://docs.litestar.dev/latest/usage/middleware/builtin-middleware.html)). | The server has no CORS config today, so embedding needs an HTTPS API origin plus `CORSConfig`. |
| Recommended path | Microsoft suggests PCF components or custom pages for «configurable, reusable, and tighter external integrations» ([web resources](https://learn.microsoft.com/en-us/power-apps/developer/model-driven-apps/web-resources)). | A web resource is the lightest option and needs no build-tool change; PCF would be a rewrite. |

## Recommendations for this repo

1. **Rename the three hyphenated modules** (for example `appealModal.js`, `criteriaTable.js`, `checklistEditor.js`). It's a mechanical rename that `tsc` checks, and without it the bundle can't be uploaded.
2. **Add a loader web resource** `cqa_/index.htm`: the existing `index.html`, but with `mountCqa(root, JSON.parse(new URLSearchParams(location.search).get('data') ?? '{}'))` replacing the hard-coded `apiBase: '/api'`. Configure `data` on the form control, e.g. `{"apiBase":"https://cqa.example.com/api"}`.
3. **Serve the API over HTTPS** (a named tunnel or a host) and add `CORSConfig(allow_origins=[env CQA_ALLOWED_ORIGINS])`, set to the org's `https://<org>.crm*.dynamics.com` origin.
4. **Proxy call audio through our API** so a Strict-CSP environment needs exactly one extra origin in `connect-src` and `media-src`.
5. **On the form control:** turn «Restrict cross-frame scripting» off, and turn «Pass record object-type code and unique identifier» on if a card should open for the current record.
6. Before claiming «works in D365», do one smoke test in a trial environment: upload `cqa_/dist/**`, `cqa_/cqa.css` and `cqa_/index.htm`, then open them with `navigateTo`.
